## 3. Different from what the audit predicted

**H2 — my audit's root cause was wrong, and the prescribed fix would have done nothing.**

The audit said Next's streamed-metadata shell emits a placeholder `noindex` for routes absent from `generateStaticParams`, and that `htmlLimitedBots` would fix it. Reading the installed Next 16.3.0 source, the only place that string is emitted is `dist/esm/server/app-render/make-get-server-inserted-html.js:28-32`, guarded by `isHTTPAccessFallbackError(error)` — i.e. a **captured `notFound()`**, nothing to do with bot detection or streaming.

I tested the prescribed scenario directly: published a visa record without redeploying and fetched the route. **Zero noindex tags, one `index, follow`.** The failure does not reproduce, so `htmlLimitedBots` would have added a blocking-render TTFB cost for bots to fix a bug that isn't there. I did not implement it.

What I did instead addresses the real mechanism. `generateMetadata` and the page body each called `load()` independently — two API calls per request. If they disagree (transient 404 or timeout on one), the metadata says `index` while the body throws `notFound()`, and Next injects the `noindex` alongside it. That is exactly the two-tag output the audit observed. `load()` is now wrapped in React `cache()`, so both share one result and cannot disagree. It also halves the API calls per render.

The original Saudi `noindex` was most likely a cached render from the window when the record was still a draft. I could not reproduce that state on demand — with `revalidate = 300`, unpublishing the probe still served the cached 200 for the stale window — so I am **not claiming** to have proven that specific history, only that the ongoing risk the item was written against does not exist.

**H4 — I over-applied the FAQ change and caught it.** The first pass matched on the closing sentence alone and updated 18 documents, including `usa`, `united-kingdom` and `canada`. Those packages offer *guidance* on the reservation, not the reservation itself:

```
  canada / Standard: Guidance on the flight itinerary your application needs
  united-kingdom / Standard: Guidance on the flight reservation the Home Office expects
  usa / Standard: Guidance on the flight itinerary for your interview
```

Telling those customers the reservation is included would have been false. Reverted immediately and the script is now scoped to the six Schengen-family slugs. Final state verified per record: six `INCLUDED`, three `separate`, Saudi has no flight FAQ.

**H6 — the audit's link count was wrong.** It said 22 links across 5 files. It was 20 across 6: the audit missed `apps/visawadi-frontend/src/app/about/page.js:48` and double-counted elsewhere. Also, a naive rewrite turned the three "all destinations" links into `/uae/visa`, which is not a route; they are `/uae`.

**H3 — the overlay was contaminated too.** The audit flagged the bad pricing on the base record and only the `metaDescription` on the overlay. The AE overlay also carried the wrong package price, the 499 service fee and the dead-tier note. Since the overlay is what actually renders, fixing only the base would have changed nothing on the live page.

**H8 needed a merchandising decision.** The homepage renders the first six of a fixed `DESTINATION_ORDER`, and `saudi-arabia` was not in it, so no homepage link was possible without a change. I placed it fifth, which displaces `germany-visa` from the visible six. One line in `apps/visawadi-frontend/src/app/page.js:118-128` if you want a different order.
